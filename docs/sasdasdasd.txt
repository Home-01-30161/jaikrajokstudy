## 1. เริ่มต้นใน 5 นาที

```bash
# 1. clone repo ของทีม
git clone https://gitlab.nectec.or.th/ai4thai-service-hackatho/<team-XX>/<repo-name>
cd <reponame>

# 2. แก้โค้ดตามใจ แล้ว push ขึ้น main
git add .
git commit -m "first deploy"
git push origin main

# 3. รอ pipeline เสร็จ (ดูที่ GitLab > Build > Pipelines)

# 4. เปิดเว็บ
# https://team01.aiforthai.in.th
```

pipeline จะรัน 2 ขั้น: **validate** (ตรวจ compose) แล้ว **deploy** (build + up)
ถ้า validate ไม่ผ่าน deploy จะไม่ทำงาน — อ่าน error ใน job log แล้วแก้ตามนั้น

## 2. URL ของทีม

แทน `NN` ด้วยเลขทีมของคุณ (`01`–`15`)

| URL | คืออะไร |
| --- | --- |
| `https://teamNN.aiforthai.in.th/` | frontend |
| `https://teamNN.aiforthai.in.th/api/` | backend API |
| `https://teamNN.aiforthai.in.th/logs/` | หน้าดู log ของทีม |

ทั้งหมดเป็น **HTTPS** และเป็น **โดเมนเดียวกัน** (same-origin)
frontend กับ api อยู่โดเมนเดียวกัน จึงไม่มีปัญหา CORS และไม่ต้องตั้ง base URL ของ API

## 3. Port ที่ทีมได้รับ

แต่ละทีมได้ **10 port** คำนวณจาก

```
base = 20000 + (เลขทีม - 1) × 10
```

| ทีม | ช่วง port | frontend | api | สำรอง |
| --- | --- | --- | --- | --- |
| team01 | 20000–20009 | 20000 | 20001 | 20002–20009 |
| team02 | 20010–20019 | 20010 | 20011 | 20012–20019 |
| team03 | 20020–20029 | 20020 | 20021 | 20022–20029 |
| … | … | … | … | … |
| team15 | 20140–20149 | 20140 | 20141 | 20142–20149 |

**หา base ของทีมตัวเองเร็ว ๆ**

```bash
N=1                       # เลขทีมของคุณ
echo $((20000 + (N-1)*10))
```

### กติกาเรื่อง port

- **bind `127.0.0.1` เท่านั้น** — ห้าม `0.0.0.0` หรือเขียนแค่ `"20000:3000"`
- ใช้ได้เฉพาะช่วงของทีมตัวเอง
- service ที่ไม่ต้องเข้าจากข้างนอก (db, redis, qdrant) **ไม่ต้อง bind ออก host เลย** เรียกผ่านชื่อ service ได้

```yaml
# ถูก
ports:["127.0.0.1:20000:3000"]

# ผิด — pipeline จะไม่ผ่าน
ports:["20000:3000"]
ports:["0.0.0.0:20000:3000"]
ports:["127.0.0.1:20050:3000"]   # นอกช่วงของทีม
```

```
├── .env.example

```

```
team01/
└── .gitlab-ci.yml         # ทีมเขียนเอง — ก๊อปจาก template ที่ทีมงานให้
```

**ทีมเป็นเจ้าของ `.gitlab-ci.yml` เอง** ก๊อป template ที่ให้มาวางที่ root ของ repo
แก้ 3 บรรทัดในบล็อก `variables` ให้ตรงกับทีม แล้วเพิ่ม stage อะไรก็ได้ตามใจ (test, lint, e2e)

## 4.1 gitlab-ci.yml — template

```yaml
# ============================================================
#  .gitlab-ci.yml — วางไว้ที่ root ของ repo ทีม
#
#  แก้ 3 บรรทัดในบล็อก variables ให้ตรงกับทีมตัวเอง แล้วใช้ได้เลย
#  ที่เหลือแก้ได้ตามใจ เพิ่ม test / lint / stage อื่นได้
#
#  runner ผูกกับ subgroup ของทีม — ทีมอื่นใช้ runner ของเราไม่ได้ และเราก็ใช้ของเขาไม่ได้
#
#  base = 20000 + (เลขทีม - 1) * 10
#     team01 -> BASE 20000  BASE_1 20001
#     team02 -> BASE 20010  BASE_1 20011
#     team05 -> BASE 20040  BASE_1 20041
#     team10 -> BASE 20090  BASE_1 20091
#     team15 -> BASE 20140  BASE_1 20141
# ============================================================

variables:
  TEAM:   "team01"      # <<< แก้ตรงนี้
  BASE:   "20000"       # <<< แก้ตรงนี้
  BASE_1: "20001"       # <<< แก้ตรงนี้

stages: [check, deploy, ops]

default:
  # runner ผูกกับ subgroup ของทีมอยู่แล้ว ปกติไม่ต้องใส่ tags
  #
  # ถ้า job ค้าง pending ไม่ยอมรัน แปลว่า runner มี tag แต่ job ไม่ได้ระบุ
  # ดู tag ได้ที่ Group > Settings > CI/CD > Runners แล้วปลดคอมเมนต์บรรทัดล่าง
  # tags: [<tag ที่เห็น>]
  image: docker:27.3.1
  before_script:
    # image บางเวอร์ชันไม่มี compose plugin
    # error ที่ขึ้นคือ "'compose' is not a docker command" ซึ่งหลอกมาก
    - docker compose version >/dev/null 2>&1 || apk add --no-cache docker-cli-compose
    - apk add --no-cache curl bash >/dev/null
    - echo "TEAM=$TEAM  fe=$BASE  api=$BASE_1"

# ------------------------------------------------------------
#  ตรวจ compose ก่อน deploy — กันพลาดแล้วชนกับทีมอื่น
#  แนะนำให้เก็บไว้ ไม่ใช่บังคับ แต่ถ้าลบแล้วผิดกติกาจะรู้ตอนพังแล้ว
# ------------------------------------------------------------
check:
  stage: check
  script:
    - |
      LO=$BASE; HI=$((BASE+9)); FAIL=0

      echo "== port binding =="
      while read -r line; do
        case "$line" in
          *'${BASE'*|*'$BASE'*) echo "  ok (ตัวแปร) $line" ;;
          *127.0.0.1:*)
            p=$(echo "$line" | sed -n 's/.*127\.0\.0\.1:\([0-9]\+\):.*/\1/p')
            if [ -n "$p" ] && { [ "$p" -lt "$LO" ] || [ "$p" -gt "$HI" ]; }; then
              echo "  ❌ port $p นอกช่วงของ $TEAM ($LO-$HI)"; FAIL=1
            else echo "  ok $line"; fi ;;
          *) echo "  ❌ ไม่ได้ bind 127.0.0.1 -> $line"; FAIL=1 ;;
        esac
      done < <(grep -E '^\s*-\s*"?[0-9.$][^:]*:[0-9$]' docker-compose.yml || true)

      echo "== bind mount =="
      for m in $(grep -oE '^\s*-\s*[./][^:]*:' docker-compose.yml | sed 's/^\s*-\s*//; s/:$//' || true); do
        case "$m" in
          */var/run/docker.sock*) echo "  ❌ ห้าม mount docker.sock — ใช้ /logs/ แทน"; FAIL=1 ;;
          ./*|../*) echo "  ❌ relative bind mount: $m (resolve ที่ host ข้อมูลจะหาย)"; FAIL=1 ;;
          /data/hack/*) echo "  ok $m" ;;
          /*) echo "  ❌ bind mount นอก /data/hack: $m"; FAIL=1 ;;
        esac
      done

      echo "== อื่น ๆ =="
      grep -q 'memory:'      docker-compose.yml || { echo "  ❌ ไม่มี memory limit"; FAIL=1; }
      grep -q 'healthcheck:' docker-compose.yml || { echo "  ❌ api ต้องมี healthcheck"; FAIL=1; }
      grep -q 'max-size'     docker-compose.yml || { echo "  ❌ ไม่มี logging max-size"; FAIL=1; }

      [ $FAIL -eq 0 ] && echo "ผ่านทั้งหมด" || { echo "แก้ให้ผ่านก่อน — สงสัยถาม ทีมงาน"; exit 1; }

# ------------------------------------------------------------
#  Deploy
# ------------------------------------------------------------
deploy:
  stage: deploy
  timeout: 20m
  interruptible: true
  environment:
    name: $TEAM
    url: https://$TEAM.aiforthai.in.th
  script:
    # secret มาจาก CI/CD Variables ที่ขึ้นต้นด้วย APP_ (ตั้งเป็น Masked)
    # อย่าใส่ set -x ในสเต็ปนี้ ค่าจะโผล่ใน job log
    - printenv | grep '^APP_' > .env || true
    - docker compose -p "$TEAM" up -d --build --remove-orphans
    - |
      echo "รอ healthcheck..."
      for i in $(seq 1 40); do
        st=$(docker inspect -f '{{.State.Health.Status}}' "${TEAM}-api-1" 2>/dev/null || echo none)
        [ "$st" = "healthy" ] && { echo "api healthy"; break; }
        sleep 5
      done
      docker compose -p "$TEAM" ps
    - curl -fsS "http://127.0.0.1:${BASE_1}/health" && echo " <- /health OK"
  rules:
    - if: $CI_COMMIT_BRANCH == "main"

# ============================================================
#  Manual jobs — กดเองได้จากหน้า Pipelines (ใช้แทน SSH)
# ============================================================
.ops: &ops
  stage: ops
  when: manual
  allow_failure: true
  interruptible: false

logs:
  <<: *ops
  script: [docker compose -p "$TEAM" logs --tail=400 --timestamps --no-color]

ps:
  <<: *ops
  script:
    - docker compose -p "$TEAM" ps
    - docker stats --no-stream $(docker compose -p "$TEAM" ps -q) || true

restart:
  <<: *ops
  script:
    - docker compose -p "$TEAM" restart
    - docker compose -p "$TEAM" ps

migrate:
  <<: *ops
  # -T สำคัญมาก ไม่งั้น job ค้างรอ TTY จนหมด timeout
  script: [docker compose -p "$TEAM" exec -T api alembic upgrade head]

shell-cmd:
  <<: *ops
  variables:
    SERVICE: api
    CMD: "python -c 'import sys; print(sys.version)'"
  script: [docker compose -p "$TEAM" exec -T "$SERVICE" sh -lc "$CMD"]

reset-db:
  <<: *ops
  script:
    - docker compose -p "$TEAM" stop db
    - docker compose -p "$TEAM" rm -f db
    - rm -rf /data/hack/$TEAM/pgdata/*      # bind mount ไม่ใช่ named volume
    - docker compose -p "$TEAM" up -d
```

## 5. docker-compose.yml — กติกาและตัวอย่าง

CI จะส่งตัวแปรมาให้อัตโนมัติ **ไม่ต้องแก้เอง**

| ตัวแปร | ค่า (ตัวอย่าง team01) |
| --- | --- |
| `${TEAM}` | `team01` |
| `${BASE}` | `20000` |
| `${BASE_1}` | `20001` |

### ตัวอย่างเต็ม

```yaml
name: ${TEAM}

x-logging: &logging
  driver: json-file
  options:
    max-size: "50m"
    max-file: "3"

x-common: &common
  restart: unless-stopped
  logging: *logging
  networks: [app]

services:
  frontend:
    <<: *common
    build: ./frontend
    ports:
      - "127.0.0.1:${BASE}:3000"
    environment:
      NODE_ENV: production
    depends_on:
      api:
        condition: service_healthy
    deploy:
      resources:
        limits:
          memory: 2G
          cpus: "2.0"

  api:
    <<: *common
    build: ./api
    ports:
      - "127.0.0.1:${BASE_1}:8000"
    env_file:
      - .env
    environment:
      DATABASE_URL: postgresql+psycopg://app:${TEAM}pass@db:5432/app
      REDIS_URL: redis://redis:6379/0
      QDRANT_URL: http://qdrant:6333
      ROOT_PATH: /api
    volumes:
      - /data/hack/${TEAM}/uploads:/app/uploads
    healthcheck:
      test: ["CMD", "curl", "-fsS", "http://localhost:8000/health"]
      interval: 15s
      timeout: 5s
      retries: 3
      start_period: 40s
    depends_on:
      db:
        condition: service_healthy
      redis:
        condition: service_started
    deploy:
      resources:
        limits:
          memory: 4G
          cpus: "4.0"

  db:
    <<: *common
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: ${TEAM}pass
      POSTGRES_DB: app
    volumes:
      - /data/hack/${TEAM}/pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d app"]
      interval: 10s
      timeout: 5s
      retries: 6
    deploy:
      resources:
        limits:
          memory: 2G
          cpus: "2.0"

  redis:
    <<: *common
    image: redis:7-alpine
    command: ["redis-server", "--save", "60", "1", "--appendonly", "no"]
    deploy:
      resources:
        limits:
          memory: 512M
          cpus: "1.0"

  qdrant:
    <<: *common
    image: qdrant/qdrant:latest
    volumes:
      - /data/hack/${TEAM}/qdrant:/qdrant/storage
    deploy:
      resources:
        limits:
          memory: 4G
          cpus: "2.0"

networks:
  app:
    driver: bridge
```

### ห้ามแก้ 5 อย่างนี้

1. `ports` ต้อง bind `127.0.0.1` และอยู่ในช่วงของทีม
2. `deploy.resources.limits` ต้องมีทุก service
3. `healthcheck` ของ `api` ต้องมี
4. `logging` options ต้องมี (ไม่งั้น log จะกินดิสก์จนล่มทั้งเครื่อง)
5. bind mount ต้องเป็น absolute path ใต้ `/data/hack/${TEAM}`

### เพิ่ม service เองได้

เพิ่ม worker, celery, scraper อะไรก็ได้ — แค่อย่า bind port ออก host ถ้าไม่จำเป็น
ถ้าต้องเข้าจากข้างนอกจริง ๆ ดูหัวข้อ **ขอเปิด service เพิ่ม**

### resource ที่ได้

| service | RAM | CPU |
| --- | --- | --- |
| frontend | 2 GB | 2.0 |
| api | 4 GB | 4.0 |
| postgres | 2 GB | 2.0 |
| qdrant | 4 GB | 2.0 |
| redis | 512 MB | 1.0 |

ปรับได้ตามต้องการ แต่อย่าให้รวมเกิน ~13 GB ต่อทีม

## 6. Frontend — เรียก API ยังไง

**เรียกด้วย relative path เสมอ**

```jsx
// ถูก — same-origin ใช้ได้ทั้ง localhost และบนเซิร์ฟเวอร์
const res = await fetch('/api/chat', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ message: 'สวัสดี' })
});
```

```jsx
// ผิด — hardcode host แล้วจะพังตอนขึ้นเซิร์ฟเวอร์
const res = await fetch('http://localhost:8000/chat', ...);
```

### Streaming (SSE)

เซิร์ฟเวอร์ตั้งค่าไม่ให้ buffer ไว้แล้ว stream ได้ตามปกติ

```jsx
const res = await fetch('/api/chat/stream', {
  method: 'POST',
  body: JSON.stringify({ message: 'สวัสดี' })
});

const reader = res.body.getReader();
const decoder = new TextDecoder();

while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  console.log(decoder.decode(value));   // ทยอยมาทีละชิ้น
}
```

### dev บนเครื่องตัวเอง

ตั้ง proxy ใน dev server ให้ `/api` ชี้ไป backend จะได้เขียนโค้ดชุดเดียวใช้ได้ทั้งสองที่

```jsx
// next.config.js
module.exports = {
  async rewrites() {
    return [{ source: '/api/:path*', destination: 'http://localhost:8000/:path*' }];
  }
};
```

```jsx
// vite.config.js
export default {
  server: {
    proxy: { '/api': { target: 'http://localhost:8000', rewrite: p => p.replace(/^\/api/, '') } }
  }
};
```

## 7. Backend — ตั้งค่าที่ต้องมี

### 1) `root_path` (สำคัญมาก)

reverse proxy จะ **ตัด `/api` ออก** ก่อนส่งเข้ามาที่ container
ทีมเขียน route ปกติ (`/health`) แต่เรียกจากข้างนอกเป็น `/api/health`

ถ้าไม่ตั้ง `root_path` หน้า `/docs` กับ `/openapi.json` จะพัง

```python
# FastAPI
import os
from fastapi import FastAPI

app = FastAPI(root_path=os.getenv("ROOT_PATH", ""))

@app.get("/health")
def health():
    return {"status": "ok"}
```

```jsx
// Express — ใช้ router prefix ไม่ได้ เพราะ path ถูกตัดมาแล้ว
app.get('/health', (req, res) => res.json({ status: 'ok' }));
```

### 2) `/health` endpoint (บังคับ)

ต้องตอบ HTTP 200 เมื่อพร้อมใช้งาน ระบบใช้ endpoint นี้เช็คว่า deploy สำเร็จไหม
ถ้าไม่มี pipeline จะรอจนหมดเวลาแล้ว fail

### 3) bind `0.0.0.0` ใน container

```python
uvicorn.run(app, host="0.0.0.0", port=8000)
```

`127.0.0.1` ใน container จะทำให้ Docker เข้าไม่ถึง (คนละเรื่องกับการ bind port ของ host)

### 4) migration อัตโนมัติ

ใส่ใน entrypoint จะได้ไม่ต้องกดเอง

```docker
CMD sh -c "alembic upgrade head && uvicorn app.main:app --host 0.0.0.0 --port 8000"
```

## 8. Deploy ผ่าน GitLab CI

### ตั้งค่าครั้งแรก

1. ก๊อป `.gitlab-ci.yml` template ที่หัวข้อ 4.1 ที่ทีมงานให้ ไปวางที่ root ของ repo
2. แก้ `variables` ให้ตรงกับทีม

```yaml
variables:
TEAM:"team01"
BASE:"20000"
BASE_1:"20001"
```

1. commit + push ขึ้น `main`

> `runner` ผูกกับ subgroup ของทีมอยู่แล้ว ทีมอื่นใช้ไม่ได้ และเราก็ใช้ของทีมอื่นไม่ได้
ถ้า job ค้าง `pending` ไม่ยอมรัน ให้ดูหัวข้อแก้ปัญหา
> 

### วิธี deploy

push ขึ้น branch `main` → pipeline รันเอง

| Stage | ทำอะไร |
| --- | --- |
| `check` | ตรวจ `docker-compose.yml` ตามกติกา |
| `deploy` | build + `docker compose up -d` + รอ healthcheck |

branch อื่นจะรันแค่ `check` ไม่ deploy — ใช้เช็คว่า compose ถูกต้องก่อน merge ได้

### แก้ pipeline เองได้

เพิ่ม stage อะไรก็ได้ — unit test, lint, build cache, e2e

**แต่แนะนำให้เก็บ job `check` ไว้** มันตรวจกติกาเรื่อง port กับ bind mount ให้
ถ้าลบทิ้งแล้วเขียนผิด จะไปรู้ตอนของพังหรือชนกับทีมอื่นแล้ว

### อ่าน error

GitLab → **Build → Pipelines** → คลิก job ที่แดง → อ่าน log

- **validate แดง** → compose ผิดกติกา อ่านบรรทัด ❌ แล้วแก้ตามนั้น
- **deploy แดงตอน build** → Dockerfile หรือ dependency มีปัญหา
- **deploy แดงตอนรอ health** → container ขึ้นแล้วแต่ `/health` ไม่ตอบ ดู log ผ่านปุ่ม `logs`

### ข้อจำกัด

- job timeout **20 นาที** — build เกินจะถูกตัด
- ทีมละ 3 job พร้อมกัน

## 9. คำสั่งที่กดเองได้ (แทน SSH)

ทีมไม่มีสิทธิ์ SSH เข้าเซิร์ฟเวอร์ แต่ทำได้เกือบทุกอย่างผ่านปุ่มใน GitLab

ไปที่ **Build → Pipelines** → เลือก pipeline → ใน stage `ops` จะมีปุ่ม ▶ ให้กด

| Job | ทำอะไร |
| --- | --- |
| `logs` | ดู log ล่าสุด 400 บรรทัด ทุก service |
| `ps` | ดูสถานะ container + RAM/CPU ที่ใช้ + พื้นที่ดิสก์ |
| `restart` | restart ทุก container ของทีม |
| `migrate` | รัน `alembic upgrade head` |
| `shell-cmd` | รันคำสั่งอะไรก็ได้ใน container |
| `reset-db` | **ลบ database ทั้งหมด** แล้วสร้างใหม่ |

### วิธีใช้ `shell-cmd`

กดปุ่ม ▶ แล้วใส่ตัวแปร:

| Key | Value ตัวอย่าง |
| --- | --- |
| `SERVICE` | `api` |
| `CMD` | `python -c "from app.db import init; init()"` |

ตัวอย่างที่ใช้บ่อย

```bash
# ดู env ที่ container เห็นจริง
printenv | sort

# ทดสอบต่อ database
python -c "import psycopg; print('db ok')"

# seed ข้อมูล
python scripts/seed.py

# เข้า psql
# SERVICE=db  CMD=psql -U app -d app -c "\dt"
```

> `reset-db` ลบข้อมูลถาวร กู้ไม่ได้ ใช้ตอนแน่ใจเท่านั้น

## 12. Environment variable และ secret

### ค่าที่ไม่ลับ

ใส่ใน `docker-compose.yml` ตรง ๆ หรือ commit `.env` ลง repo ได้เลย

### ค่าที่ลับ (API key, token)

**ห้าม commit ลง repo** ให้ใส่ใน GitLab แทน

1. ไปที่ **Settings → CI/CD → Variables → Add variable**
2. ตั้งชื่อขึ้นต้นด้วย `APP_` เช่น `APP_OPENAI_API_KEY`
3. ติ๊ก **Masked** เพื่อไม่ให้โผล่ใน job log
4. deploy job จะเขียนตัวแปรทั้งหมดที่ขึ้นต้นด้วย `APP_` ลง `.env` ให้อัตโนมัติ

```yaml
services:
api:
env_file:[.env]      # อ่าน APP_* ที่ CI สร้างให้
```

### ห้ามใส่ API key ใน frontend

key ที่อยู่ใน frontend จะเห็นได้จาก DevTools ของใครก็ได้

```
❌  browser → LLM API โดยตรง (key หลุด)
✅  browser → /api/chat ของทีม → LLM API (key อยู่ฝั่ง backend)
```

## 13. ขอเปิด service เพิ่ม

ปกติทีมได้ 2 ทาง (`/` และ `/api/`) ถ้าอยากเพิ่มเช่น Adminer, MCP server, worker dashboard

**แจ้งที่ทีมงาน** บอก 3 อย่าง:

1. ทีม (เช่น `team01`)
2. port ที่จะใช้ — ต้องอยู่ในช่วงสำรองของทีม (`base+2` ถึง `base+9`)
3. path ที่อยากได้ (เช่น `/db/`) และต้องการรหัสผ่านป้องกันไหม

ทีมงานเปิดให้ภายในไม่กี่นาที

**ทีมต้อง bind port เองใน compose ด้วย** ไม่งั้นจะได้ 503

```yaml
adminer:
image: adminer:standalone
ports:["127.0.0.1:20002:8080"]     # team01 ขอ port 20002
environment:{ADMINER_DEFAULT_SERVER: db}
```

> path `/api/` และ `/logs/` ถูกใช้แล้ว ขอ path อื่น
>

## 14. กติกาที่ห้ามผิด

| ห้าม | เพราะ |
| --- | --- |
| bind port เป็น `0.0.0.0` | เปิดสู่อินเทอร์เน็ตโดยไม่ผ่าน proxy |
| ใช้ port นอกช่วงของทีม | ชนกับทีมอื่น |
| mount `/var/run/docker.sock` | เท่ากับได้สิทธิ์ root บนเครื่อง |
| แตะ container / ข้อมูลของทีมอื่น | **ตัดสิทธิ์จากการแข่งขัน** |
| รัน `docker system prune` เอง | กระทบทุกทีม |
| ลบ memory limit / logging config | ทีมเดียวทำเครื่องล่มได้ทั้งงาน |
| ใส่ secret ลง repo | ดูหัวข้อ 12 |

การกระทำทุกอย่างผ่าน CI มี log บันทึกไว้ว่าใครทำอะไรตอนไหน

## 15. แก้ปัญหาที่เจอบ่อย

### เปิดเว็บแล้วขึ้น 503

container ยังไม่ขึ้น หรือขึ้นแล้วตาย

```
1. กดปุ่ม ps    ดูว่า container รันอยู่ไหม
2. กดปุ่ม logs  หาบรรทัดที่ error
3. เปิด /logs/  ดู log realtime
```

สาเหตุที่พบบ่อย: แอป bind `127.0.0.1` แทน `0.0.0.0` ใน container

### เรียก `/api/...` แล้วได้ 404

route ในแอปเขียนผิด — จำไว้ว่า **proxy ตัด `/api` ออกแล้ว**

```
เรียกจากข้างนอก:  /api/chat
แอปต้องมี route:  /chat        ← ไม่ใช่ /api/chat
```

### `/api/docs` เปิดไม่ได้

ยังไม่ได้ตั้ง `root_path="/api"` ใน FastAPI (ดูหัวข้อ 7)

### Streaming ค้าง ไม่ทยอยมา

- ฝั่ง backend ต้องไม่ buffer เอง — FastAPI ใช้ `StreamingResponse`
- อย่าตั้ง `Content-Length` เอง
- ทดสอบด้วย `curl -N https://teamNN.aiforthai.in.th/api/stream` ถ้า curl ทยอยมาแต่เบราว์เซอร์ไม่มา ปัญหาอยู่ที่โค้ด frontend

### pipeline ค้างไม่จบ

มักเกิดจากคำสั่งที่รอ input เช่น `apt install` ที่ไม่ใส่ `-y`
ใส่ `-y` หรือ `DEBIAN_FRONTEND=noninteractive` ให้ครบ

### Build ช้ามาก

- เรียง `COPY` ให้ dependency มาก่อนโค้ด จะได้ใช้ cache
- อย่า `COPY . .` ก่อน `pip install`
- ใส่ `.dockerignore` ตัด `node_modules`, `.git`, `__pycache__`

### แก้โค้ดแล้วแต่ของเก่ายังอยู่

pipeline deploy เฉพาะ branch `main` — เช็คว่า push ถูก branch

### `check` ไม่ผ่าน

อ่านบรรทัดที่ขึ้น ❌ ใน job log แล้วแก้ตามนั้น ทุกข้อมีคำอธิบายกำกับ

### Job ค้าง `pending` ไม่ยอมรัน

ไม่มี runner ที่ตรงเงื่อนไข มัก 2 สาเหตุ

1. **runner มี tag แต่ job ไม่ได้ระบุ** — ดู tag ที่ **Group → Settings → CI/CD → Runners**
แล้วใส่ใน `.gitlab-ci.yml`

```yaml
default:
tags:[<tag ที่เห็น>]
```

1. **runner offline** — แจ้ง `ทีมงาน`

## 16. คำถามที่ถามบ่อย

**SSH เข้าเซิร์ฟเวอร์ได้ไหม**
ไม่ได้ ใช้ manual job กับ `/logs/` แทน ครอบคลุมเกือบทุกกรณี

**เปลี่ยน framework ได้ไหม**
ได้ ใช้อะไรก็ได้ที่รันใน Docker ได้ ขอแค่ frontend ฟัง 3000 และ api ฟัง 8000 ใน container (ถ้าอยากใช้ port อื่นใน container ก็แก้ฝั่งขวาของ `ports` ได้)

**เพิ่ม service ได้กี่ตัว**
ไม่จำกัด ตราบใดที่รวมกันไม่เกิน resource ที่ได้

**ข้อมูลหายไหมเวลา redeploy**
ไม่หาย เก็บอยู่ที่ `/data/hack/teamNN/` แต่ `reset-db` ลบถาวร

**deploy พร้อมกันหลายทีมได้ไหม**
ได้ ทุกทีมมี runner แยกของตัวเอง

**ใช้ GPU ได้ไหม**
ไม่ได้ เครื่องนี้เป็น CPU อย่างเดียว

**เข้าเว็บทีมอื่นได้ไหม**
เข้าดูหน้าเว็บได้ (public) แต่แตะ container หรือข้อมูลไม่ได้

**deploy ได้กี่ครั้ง**
ไม่จำกัด แต่ละครั้งใช้เวลาตาม build
